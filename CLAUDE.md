# Comaney: Agent Reference

## Rules
- Never use em-dash '—'; use ':', ';', or rewrite
- Never commit, push, or publish
- Only analyze, modify, create, or delete files and run commands
- Updating a feature: keep CLAUDE.md, AGENTS.md, and docs/src/ in sync
- New functional features or fixes: must add tests
- Always code in a way a human can maintain it!
- Use best practices, Don't repeat yourself (DRY), clear architecture
- Never load anything from the internet after deployment, except AI interaction with Anthropic and YubiKey OTP validation server calls
- All assets (fonts, images, scripts, libraries, etc.) must be served locally: either a plain JS file under `build/js/`/`static/` or a package installed with yarn (preferred) and bundled via esbuild; never a `<script src="https://...">`/CDN reference

## Stack
- Python 3.12, Django, Gunicorn, WhiteNoise, mysqlclient, MariaDB
- SCSS: `build/scss/` -> `static/dist/main.css`
- JS: `build/js/` -> `static/dist/` via esbuild
  - `expenses.js`: Alpine.js v3, bundled `--target=es2020` (required)
  - `dashboard.js`: Alpine.js v3 + Chart.js
- Build assets: `build/build-assets.sh` (Docker container, never run npm directly on host)
- CSS theming: CSS custom properties (`--var`) only, never SCSS `$vars` (breaks dark mode)
- Run `docker-compose up -d` to start the stack but it should already be running at http://localhost:8080

## Auth
- Custom `FeUser` model, not `django.contrib.auth.User`
- Session key: `request.session["feuser_id"]`; load via `_get_session_feuser(request)`
- Never use `request.user`, `login()`, or `@login_required`
- REST API: Bearer token -> `FeUser.api_key`

## Glossary

- **feuser**: an app user, backed by the custom `FeUser` model (not `django.contrib.auth.User`). Session key `request.session["feuser_id"]`.
- **expense**: a single spending record (`budget.Expense`). Always has exactly one `owning_feuser` (the "owner").
- **owner / owning expense**: the feuser recorded as `Expense.owning_feuser`. Only the owner's own `category`/`tags` fields on the `Expense` row itself count as "their" classification of it.
- **foreign expense**: an expense the current feuser did not create (is not the `owning_feuser`) but is a **participant** on, via a `BuddySpending` row.
- **participant**: a feuser (or offline dummy) with a `BuddySpending` row against an expense they don't own, representing their share of that spend.
- **expense overlay** (`ExpenseDataOverlay`): a participant's personal category, tags, and note for a foreign expense, stored separately from the expense itself (one row per `(expense, feuser)`). Lets each participant classify a shared expense their own way without affecting the owner's or other participants' classification. Never stored empty; deleted instead of zeroed (see `budget/services.py::upsert_overlay`).
- **category**: a single label (`budget.Category`) an expense (or overlay) can have. Owned per-feuser; one category per expense.
- **tag(s)**: zero or more labels (`budget.Tag`) an expense (or overlay) can have. Owned per-feuser; a plain many-to-many relation.
- **direct buddy**: another feuser (or offline dummy) you split expenses with directly, outside of any project.
- **project**: a shared group of members (`buddies.Project`) that expenses can belong to; formerly called "Buddy Group".
- **project member**: a feuser or dummy belonging to a project (`buddies.ProjectMember`).
- **partner**: another feuser in the same Catalog Partnership as you (shared category/tag catalog mapping) - distinct from "buddy".
- **dummy / offline member / offline buddy**: a non-feuser participant (`buddies.DummyUser`) standing in for someone without an account.
- **settlement**: an expense with `is_buddies_settlement=True` recording a debt payoff between two participants, not a real spend.

## Key conventions

**Projects** (`buddies/`): renamed from "Buddy Groups"; DB aliases still exist. `Expense.project` FK links to project. Call `project.update_lastmod()` on every mutation. The project page has three tabs, each its own view/URL/template sharing the `buddies/_project_tabs_header.html` partial (hero, tab nav) and a `_project_common_context(feuser, project, active_tab)` helper (`buddies/views/projects.py`) for the identity/membership/breakdown context all three need: **Expense list** (`project_detail`, default, `/projects/<id>/`) has the total-spending header, pending items, settle-up tools ("Pay someone back", "Clear everything at once"), and the expense list/filters; **Insights** (`project_insights`, `/projects/<id>/insights/`) has the balances + D3 debt graphs, spending-breakdown pie chart, spending-over-time line chart, and spending-by-tag bar chart, laid out via `.insights-grid`/`.insights-card` (2-3 col grid, collapses to 1 col under `560px`, see `_buddies.scss`); **Settings** (`project_settings`, `/projects/<id>/settings/`, admin-focused, renamed from "Manage") has the member list and admin-only actions. Solo projects hide the debt graph, pie chart, and settlement sections regardless of tab. Archived projects block mutations except confirming in-flight settlements. `Project.permission_laxity` (`PERMISSION_LAXITY_ADMIN_ONLY=0` default, `PERMISSION_LAXITY_MEMBERS=1`) governs who may edit name/description/picture: gate all three via `project.can_edit_details(feuser)` (admin always true; other members only when laxity is `MEMBERS`). Admin sets it via a dropdown on the Settings tab (`project_set_permission_laxity` view, admin-only). Everything else (invites, transfer, archive, delete) stays admin-only.

**Achim Archive**: removing a DummyUser merges their history into a special `is_archive=True` dummy instead of deleting it. Service: `BuddyArchiveService` in `buddies/services/archive.py`.

**Participant approvals** (`BuddySpending.approval_state`/`consent_set_at`, the Check/X consent shown per-participant): applies equally to direct buddy and project expenses. When the owner edits a shared expense and changes the title, value, participants, or any share, all participants' approvals reset (state -> `APPROVAL_NEUTRAL`, `consent_set_at` -> `None`). Editing only unrelated fields (payee, note, category, date) preserves approvals. The "your approval was reset" note in the update email goes only to participants who had actually approved beforehand (not neutral/rejected). `set_buddy_spendings` always deletes/recreates rows (fresh = reset); `expense_edit` decides reset-vs-preserve via `BuddyExpenseService.spend_signature`/`snapshot_approvals`/`restore_approvals`/`reset_participant_approvals`, and passes `reset_participant_pks` (the previously-approved pks) into `BuddyEmailService.notify_expense_updated`.

**Settlements**: debtor creates with `settled=True, buddy_approved=False`; balance clears only when creditor confirms (`buddy_approved=True`). Settlement expenses must never appear in "Did you pay for this?" (`pending_as_expense_owner` filters `settled=False`).

**Second factors** (`feusers/second_factor_registry.py`): TOTP, WebAuthn, Email, and YubiKey OTP are all `SecondFactorAuth` subclasses registered via `register_factor_type(FactorType(...))`; login, removal, profile, rename, and test views drive entirely off this registry (`factor_type_for`, `get_all_factors`, `method_key_of`) and never branch on a method name, so a further method needs only a model + one registration call. Login-time verification for a given method is dispatched through `_LOGIN_VERIFIERS` (`feusers/views/twofa.py`) rather than inline branching; `factor_test` (profile "Test" button, `feusers/factor_test.html`) reuses that same dispatch table and the registry's `challenge_template` partial to let a user try one specific factor in isolation (e.g. tell same-named security keys apart) without touching login/session state. `factor_rename` is a small JSON endpoint following the Categories & Tags inline-rename pattern (`.ct-name`/`.ct-name-input`, click to edit, POST on commit). The profile page's "Add new second factor" is a single `.method-dropdown` toggle (same component as the login/removal "try a different method" menus) unrolling one item per available method, rather than a separate button per method. No setup view renders its own "<method> added" confirmation screen: `second_factor_service.finish_setup(request, feuser, first)` is the shared conclusion for `totp_setup`/`webauthn_setup`/`email_factor_setup`/`yubikey_setup` alike, flashing a fresh recovery code into the session (only when `first`) and redirecting to `profile?success=2fa#section-2fa`, where `profile.html` pops and renders it once. `account_export` (`feusers/views/account.py`) includes `second_factors.csv` (method, label, is_primary, created_at via the same registry, for GDPR access requests) but deliberately never the underlying secret/credential of any method - that would hand out a working authentication bypass instead of personal data. It also includes `sankey_graph.json` (the feuser's `SankeyGraph.config_json` verbatim), added only when a graph has actually been saved (`feuser.sankey_graph` is a `OneToOneField`, absent for most feusers).

**YubiKey OTP second factor** (`feusers/yubico_otp_service.py`, `feusers/views/yubikey.py`): implements the [Yubico OTP protocol](https://developers.yubico.com/OTP/OTP_Walk-Through.html) - a signed HTTP round trip to a Yubico-protocol validation server, not local math, since there is no secret to check a code against locally. Gated instance-wide on `YUBICO_CLIENT_ID` and `YUBICO_SECRET_KEY` both being set (`yubikey_available` computed inline the same way as `webauthn_available`/`email_2fa_available`, in `profile`'s view context and `yubikey_setup`'s own guard); `YUBICO_SERVER` defaults to Yubico's own `https://api.yubico.com` if unset, but can point at a self-hosted validation server instead. `YubikeyFactor.public_id` (the fixed first 12 characters of every OTP a given physical key ever produces) is what a factor is stored and matched against - `unique=True` the same way `WebAuthnFactor.credential_id` is, since one physical key can only meaningfully be registered once across the whole instance; `yubikey_setup` checks for an existing row with that `public_id` before creating a new one and surfaces a plain "already registered" error rather than a DB integrity error. `verify_otp()`'s HTTP transport is dependency-injected (`fetch=`) purely so the signing/response-verification protocol itself is unit-testable without a network call; only its default implementation touches the network. There is no local replay/counter tracking (contrast `WebAuthnFactor.sign_count`): the validation server itself rejects a replayed OTP (`status=REPLAYED_OTP`), which `verify_otp()` treats the same as any other non-OK status.

**Email second factor** (`feusers/email_factor_service.py`, `feusers/views/email_factor.py`): `EmailFactor` is a regular TOTP secret (`feusers/models/second_factor.py`), but the code is delivered to the feuser's own inbox on request rather than read off a local authenticator app; it uses a 5-minute step (`CODE_INTERVAL`) instead of the usual 30s so the code survives email delivery lag, and the code itself is never stored anywhere (DB or cache) since pyotp recomputes it from the persisted secret + current time on every send and every verify. Capped at one `EmailFactor` per feuser (a second would always target the same address), which lets the single ajax send-code endpoint (`email_factor_send_code`) resolve its target purely from server-side session state (authenticated feuser's own factor, a mid-setup session secret, or the post-password-check pending-login factor) with zero client-supplied ids, closing off any "email an arbitrary user" abuse path. Sends are throttled via `email_factor_service.request_send` (a 60s cooldown plus a 10/hour hard cap, both via the generalized `rate_limit.is_limited`/`record_failure`, which now take optional `window`/`max_attempts` kwargs alongside their original login/TOTP brute-force defaults); the throttle bucket key is `f"{feuser_pk}:{purpose}"`, not just the pk. `purpose` is one of `"setup"` (confirming a not-yet-registered factor), `"login"` (an in-progress, not-yet-authenticated login), or `"confirm"` (an authenticated feuser acting on their own already-registered factor: `factor_test`, or a removal/recovery-regen confirm step) - `email_factor_send_code` picks it per-request based purely on session state, same as it picks the send target. Splitting these out means testing the method, or setting it up, can never block an actual login, and vice versa; it's safe because a feuser is only ever in one purpose "slot" for real - once a factor is persisted `"setup"` is unreachable for that account forever, and `"confirm"` requires already being fully authenticated, i.e. having already passed the very `"login"` gate it can't then block. On top of that, `_verify_email_login` (`feusers/views/twofa.py`, the sole dispatch target for the `"email"` key in `_LOGIN_VERIFIERS`) calls `email_factor_service.clear_login_send_throttle` the moment a code check succeeds - in *any* of those three contexts - since correctly entering the current code already proves the owner can read their inbox, so there's no reason to leave the `"login"` bucket engaged afterward (e.g. logging out and immediately signing back in). `request_send`'s `purpose` also picks between two email templates/subjects (`"setup"` uses `emails/second_factor_email_code_setup.html`; everything else falls back to the `"login"`-styled `emails/second_factor_email_code.html`, via `_TEMPLATES.get(purpose, _DEFAULT_TEMPLATE)`): telling the user they're "finishing signing in" would be misleading while they're still confirming a not-yet-registered factor. Hitting the cooldown is surfaced to the frontend as a `reason: "cooldown"` field (vs `"hourly_cap"`) so `_email_send_js.html` can show it as a reassuring "a code was already sent, check your inbox" note instead of an alarming error - the cooldown by definition means a code went out within the last 60s, well inside its 5-minute validity. The challenge/setup templates auto-trigger a send on load and show a client-side-timed "Resend code" link (`.link-button`, `feusers/templates/feusers/partials/_email_send_js.html`); availability is gated instance-wide by `email_2fa_available` (`not settings.DISABLE_EMAILING`, `feusers/context_processors.py`), same pattern as `webauthn_available`.

**Scheduled expenses** (`budget/management/commands/generate_scheduled_expenses.py`): materialization runs on the cron and synchronously on every `ScheduledExpense` create/edit. Dedup key is `Expense.scheduled_occurrence_date` (immutable, never `date_due`, never shown in any form/API). `ScheduledExpense.last_run` (financial year) gates a schedule to materialize at most once per year; `--year` bypasses the gate. `repeat_every_factor`/`repeat_every_unit` (Gate A) and `repeat_base_date`/`end_on` (Gate B) are locked on edit behind `confirm_modify_schedule` / `confirm_modify_schedule_window` (checkbox in the web form, boolean in the API PATCH body); unconfirmed changes to those fields are silently discarded server-side. Confirmed Gate A wipes and regenerates every current-year expense for the schedule (including settled ones); confirmed Gate B forces a regeneration pass that prunes now-out-of-window expenses and adds newly in-window ones, both by resetting `last_run = None` before calling `_generate_and_notify`.

**Migrations**: `./venv/bin/python3 manage.py makemigrations` to generate, then `docker-compose exec web python manage.py migrate` to apply.

**Query parser** (`budget/query_parser.py`): `apply_query(qs, query_str)`. Filters: `type=`, `settled=`, `deactivated=`, `value` (comparisons), `date` (dd.mm.yyyy / mm/dd/yyyy / yyyy-mm-dd, magic: `today`, `cur_week_start`, `cur_week_end`), `cat=`, `tag=`, `payee=`, `project=`, free-text, `||` OR, `()` grouping, `!` NOT. The "own tags/category if owner, else feuser's own `ExpenseDataOverlay`, never the foreign owner's" visibility rule for `tag=`/`cat=` exists in four shapes that must stay in sync: `_tag_q`/`_cat_q` (a Q filter for one known value), `query_parser.visible_tag_titles` (a per-expense Python check, used by the project tag bar chart in `buddies/views/projects.py`), `dashboard_cards.py`'s `_compute_chart` (a bulk ORM GROUP BY for dashboard bar/pie cards in shared mode), and `budget/unclassified.py` (the Unclassified Expenses page's own row-building, which additionally treats a missing/empty overlay as "no category, no tags" rather than just skipping it) - the middle two also scope the per-tag/category *amount* to the feuser's own `BuddySpending` share for expenses they don't own, never the full expense value.

**AI calling framework** (`budget/ai_service.py`): `AIService` is the single entry point for every AI feature in the app -- express expense creation, dashboard card AI assist (`budget/dashboard_card_ai.py`), Catalog Partnership tag/category mapping (`buddies/services/partnership_ai.py`), and Unclassified Expenses AI-solve (`budget/unclassified_ai.py`). Nowhere else constructs an `anthropic.Anthropic` client, calls `.messages.create`, or hand-parses an AI JSON response. `AIService(feuser)` resolves the feuser's own key vs. the shared trial key once (raising `AIBudgetExceededError` immediately if blocked/absent), then exposes one `prompt_*` method per feature (`prompt_express_expense_gen`, `prompt_dashboard_card_yaml`, `prompt_partnership_mapping`, `prompt_unclassified_solve`) that takes an already-assembled system prompt plus feature-specific args and returns the validated payload. Internally it owns JSON-response recovery (`_call_and_repair`: one repair AI call if the primary response doesn't parse, admin-notified either way via `ai_trial.notify_admin_json_repair_fallback`), the `{"result": "good"/"fail", ...}` envelope check (`_call_for_json`, skippable via `envelope=False` for partnership mapping and unclassified-solve, neither of which has a meaningful fail case), trial-budget billing (`_record_usage`, always fired, success or failed-after-repair), and Anthropic-exception classification (`_classify_exception`): auth/permission errors, billing-shaped rate-limit/status errors, and transient (rate-limit/overload/connection) errors each become a typed `AIAuthenticationError`/`AIBillingError`/`AITransientError`, with the billing/auth cases additionally calling `ai_trial.disable_trial`/`notify_admin_billing`/`notify_admin_invalid_trial_key` when `is_trial` -- this fires for *any* of the four features now, not just express creation. `AIService` itself never contains a line of feature prompt text or touches a domain model (`Category`/`Project`/etc.); each feature module owns assembling its own system prompt and validating the payload key it expects back (`items`/`yaml`/`mappings`/`category_uid`+`tag_uids`).

**AI express creation**: helpers in `budget/express_service.py`, view in `budget/views/express.py`; JSON response only: `{"result":"good","items":[]}` or `{"result":"fail","msg":""}`. The system prompt is assembled from independent feature blocks (`_SMART_CREATE_BASE` + `_SMART_CREATE_PROJECTS`/`_PROJECT_PARTICIPANTS`/`_PROJECT_PAYER`/`_DIRECT_BUDDY`) by `_build_smart_create_system(catalog, blocks=None)`; pass a subset to disable a capability (base is mandatory). `_select_smart_create_blocks(projects_data, single_buddies)` picks that subset per-request to save tokens: no direct buddies drops `_SMART_CREATE_DIRECT_BUDDY`; no non-archived projects drops all project fragments; projects present but none with more than one `ProjectMember` row (owner included) drops `_PROJECT_PARTICIPANTS`/`_PROJECT_PAYER` while keeping `_SMART_CREATE_PROJECTS` (so a solo project can still be picked as `project_uid`). Must be called with the same `projects_data`/`single_buddies` lists used for the catalog (see idx-desync note below), never a fresh query. The AI never sees member/buddy names as identifiers, only 0-based `idx` positions into that request's catalog list (`_build_catalog`), so it cannot reference anyone outside the catalog. Assignment fields (all mutually validated + applied client-side in `express_creation.html`, which presets the buddy section before confirm so the existing confirm path handles them): `project_uid`; project-only `project_participants` (`{idx, included, share_percent}` list, `_sanitize_project_participants` → `applyAiParticipants`) and `project_payer` (member idx, `_sanitize_project_payer` → `applyAiPayer`); direct-buddy `buddy_idx`/`buddy_paid`/`buddy_share_percent` (`_sanitize_direct_buddy` → `applyAiBuddy`; mutually exclusive with `project_uid`). An out-of-range or malformed idx is silently dropped through `_handle_invalid_ai_reference` (single choke point for future graceful correction). Pinned `share_percent` values that would overcommit a project expense (sum > 100, or sum != 100 when every included participant is pinned with none left to auto-absorb the remainder) are proportionally rescaled to sum to 100 via `_normalize_participant_shares`/`_handle_share_sum_mismatch`; a lone remaining participant is always forced to 100%. Catalog via `_build_catalog(feuser, projects_data, single_buddies)` (categories, tags, non-archived projects incl. per-member idx, direct buddies incl. idx); `projects_data`/`single_buddies` MUST be the exact same lists `_buddy_context()` (`budget/views/expenses.py`) built for that request's buddy-widget JS config (`_validate_items` takes the same two args too) -- none of `ProjectMember`, `get_actual_buddies`, or `get_dummy_buddies` have a fully deterministic ordering, so two independent queries can return members/buddies in different order and silently desync the AI's idx from the widget's arrays; reusing one query's result everywhere is what keeps idx valid. On confirm, the success banner's "View expenses" link points to `/buddies/summary/` when every saved expense is a direct buddy expense, to `/projects/<id>/` when they all belong to one project, else the expense list (via `view`/`pid` query params). Entry points: the `.fab-new-expense` FAB (expense list, and on all three project tabs via the shared `buddies/_project_fab.html` partial) opens a `.fab-wrap`/`.fab-menu` submenu (toggle wired globally in `templates/base.html` via `.fab-toggle`/outside-click, styled in `_buddies.scss` as small `.fab-menu-item` circles matching the main FAB's shape, labelled "Manual"/"AI") offering a plain link to the manual form (`title="Create manually"`) vs AI Express (`title="AI Express"`); from a project page the latter links with `?prefill=<urlencoded text>`, which `express_creation` (GET only, ignored on POST) seeds into `context["description"]` so the `.smart-input` textarea opens pre-filled with `Create all expenses for project '<name>'`. Both menu items are plain links gated by `ai_smart_create_available` (AI Express hidden entirely when unavailable), not JS-conditional.

**Unclassified Expenses** (`budget/unclassified.py`, `budget/unclassified_ai.py`, `budget/views/unclassified.py`, `/budget/unclassified/`): surfaces every expense missing a category and/or tags, from the current feuser's own point of view. An **own** expense is unclassified when `Expense.category` is null or it has zero `tags`; a **foreign** expense (feuser is a `BuddySpending` participant, not the owner) is unclassified when the feuser's own `ExpenseDataOverlay` for it has no category and no tags -- checked purely against that overlay (missing or empty alike), never the owner's own classification of the same expense. Settlement expenses (`is_buddies_settlement=True`) are never unclassified, and neither are savings deposits/withdrawals (`_EXCLUDED_TYPES = [TransactionType.SAVINGS_DEPOSIT, TransactionType.SAVINGS_WITHDRAWAL]`, applied everywhere `is_buddies_settlement=False` is) -- moving money between your own accounts isn't the kind of spend a category/tag classifies meaningfully; archived-project expenses still are (archiving blocks mutating the expense, not classifying it). `budget/unclassified.py::resolve_expense_kind`/`_build_row` are the single place that builds a "row" (own-vs-overlay resolved category/tags + a `problem` string, one of `"Category missing"`/`"Tags missing"`/`"Category and Tags missing"`/`None`), reused by the list page, the single-row save, the bulk save, and the AI-solve endpoint so they can never disagree on what a row looks like. Saving (`unclassified_save`/`unclassified_save_all`) routes own-vs-foreign exactly like `expense_edit`/`expense_edit_overlay` do (write `Expense.category`/`tags` directly vs. `budget/services.py::upsert_overlay`), which is also what creates a foreign expense's `ExpenseDataOverlay` row on the fly the first time a participant classifies it -- there is no separate "create overlay" step. The nav sidebar's red count bubble uses the same `action_badge`/`register_badge` mechanism as the other nav badges (`budget/templatetags/action_badges.py`, `"unclassified_expenses"` type), backed by a lean COUNT-only query in `budget/unclassified.py::count_unclassified_expenses` (it runs on every page load app-wide via `budget_base.html`, so it deliberately does NOT reuse the row-building path -- never a second, separately-maintained *definition* of unclassified though, both paths encode the same own/foreign rule). The AI-solve system prompt (`budget/unclassified_ai.py::build_unclassified_system_prompt`) gets the feuser's `ai_custom_instructions`, their own closed category/tag catalog (`category_tag_catalog`, shared with the page's dropdown/combobox data so they can never list different options), the expense's full metadata, and -- for a foreign expense -- the *owner's* own category/tags as read-only context to help match against the feuser's own catalog; the AI may only ever pick from that catalog (never invent a category/tag) and only ever fills a field that was actually missing (`solve_unclassified`'s merge step re-checks this server-side regardless of what the AI returns), and each call's `cost_cents` (from `AIService.last_usage`) is returned to the client and surfaced in the UI. The frontend (`build/js/unclassified.js`, `budget/templates/budget/unclassified_list.html`) is a per-row Alpine component: clicking a Category/Tags cell swaps it for a `<select>`/pill-and-typeahead combobox (filtered client-side against the same embedded catalog, no separate autocomplete endpoint), inside a `table-layout:fixed` + `<colgroup>` table so entering edit mode never shifts column widths (widths only ever change via the full-table-height drag handles injected by `_setupColResize`); any pending edit -- manual or AI-suggested -- hides "Edit" and shows "Revert"/"Save", and highlights only the actual new/changed value (never the whole cell) via `--unsaved-bg`/`--unsaved-fg` (new CSS vars, same colors as `--sav-dep-bg`/`--sav-dep-fg` but a distinct name, since that pair already means the unrelated "Savings Deposit" transaction-type color elsewhere) -- tags render per-tag so only newly-added ones get the highlight span, not pre-existing ones sitting next to them. "Let AI solve" blocks the whole view (`.unclassified-block-overlay`) while waiting, then briefly shows that call's cost before fading out (click-to-dismiss early); "Let AI resolve all" is a client-side sequential loop over the same per-row AI endpoint (skips rows already dirty, re-checking before each request) with its own non-blocking floating progress panel (running cost total + a Stop button that disables itself immediately on click, since the actual stop only takes effect after the in-flight request finishes) -- the table stays visible throughout so rows are seen filling in live. A 402 (AI budget/trial exhausted, enforced by `AIService.__init__` itself -- the same framework-level guard every AI feature gets, verified to block before any Anthropic call is made) sets `aiUnavailable` client-side, hiding every AI button on the page without touching already-applied pending changes. A `beforeunload` listener soft-blocks tab close/reload with the browser's native confirmation whenever any row is dirty. A foreign row shows a small "From `<project>`"/"From `<owner>`" caption under the title (never a pill -- project names routinely wrap a pill onto its own line and break row height), sourced from `_build_row`'s `project_title`/`owner_name`; this is a provenance label only, distinct from `create_participant_overlays`' auto-matching described below.

**AI tag suggestion on the expense/recurring-expense forms** (`budget/unclassified_ai.py::suggest_tags`, `budget/views/unclassified.py::expense_ai_suggest_tags`, `POST /budget/expenses/ai-suggest-tags/`): the "AI: select tags" button next to the Tags checkbox list in `expense_form.html`/`scheduled_form.html` (create and edit alike) reuses the exact same `solve_unclassified` prompt/response machinery as the Unclassified page's "Let AI solve", just fed the form's current, possibly-unsaved field values instead of a persisted `Expense`/`ExpenseDataOverlay` row -- there is only one place that turns expense metadata into a tag/category suggestion. `suggest_tags` always builds its row with `tag_uids: []` (unlike `solve_unclassified`'s own "never touch a field that wasn't missing" rule, which only makes sense once something is actually persisted), so the button always asks for -- and the frontend always replaces the checkbox selection with -- a fresh suggestion regardless of what's already checked; the currently-selected category, if any, is passed through as prompt context only and never returned or applied (that dropdown is this button's business, not the other one's). Both forms gate the button behind `ai_smart_create_available` and share one bundle, `build/js/expense_tag_ai.js` (`static/dist/expense_tag_ai.js`), which reads the form's plain (non-Alpine) fields by id (`id_title`/`id_payee`/`id_type`/`id_value`/`id_note`/`id_category`, and `id_date_due` or `id_repeat_base_date`, whichever exists) and shows that call's `cost_cents` next to the button the same way the Unclassified page does.

**Sankey Studio** (`budget/sankey_service.py`, `budget/sankey_generation.py`, `budget/views/sankey.py`, `budget/models/sankey.py`, `/budget/sankey/`; see `sankey-studio-spec.md` for the full design rationale): gated behind `FeUser.enable_early_access` ("Enable early access features", default `False`, profile "Early access" card, `feusers/forms.py::EarlyAccessSettingsForm`) - the sidebar link is hidden via `sankey_studio_available` (`feusers/context_processors.py`), and all three views (`sankey_studio`, `sankey_save_api`, `sankey_generate_api`) re-check `feuser.enable_early_access` directly (not the context processor, to avoid a redundant query) and refuse direct-URL access: the page view redirects to the dashboard, the two POST APIs return a 404 JSON error. This is the only early-access-gated feature so far; a future one should reuse the same `enable_early_access` flag rather than adding a new per-feature setting. Lets a feuser arrange their own Tags, Categories, and Projects (one shared pool of "nodes") into a directed flow graph and generate a Sankey chart from real expense data. There is no AI-assisted graph suggestion for this feature (tried once, removed: the AI routinely proposed nonsensical topology, e.g. tags as source/"input" nodes rather than downstream targets) - the graph is built by hand only. One `SankeyGraph` per feuser (`config_json`: `{"nodes": {...}, "edges": [...]}`, node keys `"tag:<pk>"`/`"category:<pk>"`/`"project:<pk>"`/`"connector:<token>"`), extended incrementally rather than rebuilt: a newly-created catalog entity just appears in the editor's "unplaced" palette, never auto-inserted. `budget/sankey_service.py` is the pure, Django-free routing algorithm (unit-tested in `tests/unit/test_sankey_service.py`): edges must form a DAG (`topological_order`/`CycleError`, `would_create_cycle` for live edit-time rejection), and every node's priority is a single node-owned integer (not per-edge/per-parent, settable only via its own number input field, never by scrolling the node - scroll-to-adjust was tried and dropped, it collided with scroll-to-zoom too easily) used to sort whichever siblings a given parent happens to have, tie-broken by origin type (project > category > tag) then alphabetically (`build_children_order`). Weights are computed by `partition_flow` as a top-down, first-match-wins partition, not independent per-edge sums: independent sums would double-count an expense that matches two sibling children (e.g. tagged both "Food" and "Drinks"). There is no "Other"/catch-all node type and nothing is ever auto-injected: a node whose wired real children don't collectively claim 100% of its inflow simply keeps the rest for itself, always, for every node - `node_totals` (see `partition_flow`) is computed as a node's full inflow *before* any distribution to children, so it already reflects whatever a node kept regardless of whether any of that inflow went anywhere. One mechanism covers all three of "keep everything" (no wired child matches anything, functions like a true leaf despite the drawn edges), "pass everything along" (children between them claim it all), and "keep some, pass some" (children claim part of it) - none of the three needs any special setting; `sum(inflow) == sum(outflow)` is therefore not a general invariant, only something that happens to hold when a node's children cover its whole inflow. A `connector:<token>` node (`"+ Connector node"` in the toolbar, `CATCH_ALL_TYPES` in both `sankey_service.py` and the JS) is a plain wiring shortcut with no meaning of its own, for collapsing an M-node fan-in/N-node fan-out into M+N edges through one shared hub instead of M*N direct edges: as a *child*, it's always evaluated last regardless of its own priority number and claims whatever its siblings didn't (it has no expense data of its own to match against, so `matches[connector_key]` is always `None`, same mechanism a catch-all would use) - only ever created when the user explicitly places and wires one themselves, same as any other node. Because Category and Project are each singular per expense (never two different categories, or two different projects, on the same expense), an edge between two *different* real nodes of the same one of those types could never carry any value; `is_impossible_edge` rejects such a *direct* edge with an explanatory message, both client-side at draw-time (`_tryConnect`) and server-side in `save_graph` (defense in depth). That direct-edge check isn't enough on its own though: the same impossibility exists just as much through a *chain* of intermediate nodes (a Connector hub, or even a real Tag node sitting in between) as it does through a direct edge, since once a node's inflow is provably restricted to one Category/Project (or a fixed set of them, e.g. several different income Categories all fed into one Connector), nothing downstream of it can ever carry a *different* one - this is exactly the mistake that once silently routed every expense reaching a Connector nowhere at all (5 income Categories wired through one Connector into 4 different expense Categories: every item arriving at the Connector already had one of the 5 income categories, so none of it could ever match any of the 4 downstream ones). `sankey_service.locked_identities` computes, per node and per axis (`category`/`project`), the set of identities its inflow is provably already restricted to (`None` if unrestricted - e.g. it has an unrestricted, Tag-rooted parent too), by walking the DAG backward; `is_impossible_edge_chain` uses that to reject an edge whose target's own identity isn't in its source's lock (subsumes `is_impossible_edge`'s direct case, since a Category/Project node's own lock is just its own ident regardless of its parents). `sankey_generation._check_impossible_chains` runs this over the full edge set in both `save_graph` (rejects the graph before it's persisted) and `generate()` (re-validates the already-saved graph before running the routing algorithm, so a graph that predates this check - or was otherwise saved bad - fails loudly with the offending edge named). `budget/sankey_generation.py` is the DB-facing wrapper: `_resolve_node_q` does own-if-owner-else-overlay **exact** pk matching (mirrors the visibility rule in `_tag_q`/`_cat_q` above, but those match a title *substring* for the query language, not a specific known node - reusing them here would false-positive on e.g. "Food" matching "Fast Food"; this is a new shape the existing four don't cover, not a fifth copy of one of them, and full unification is deliberately left for a follow-up rather than risking the existing four call sites). Expense scoping reuses `budget/views/_sharing.py::build_shared_qs` (shared mode: value at the feuser's own `BuddySpending` share, including for their own expenses) and the plain owner filter (individual mode: full value) - the same period + individual/shared controls as the dashboard, via `partials/_date_range_nav.html`; both branches of `_scoped_expense_qs` are additionally filtered to `type=TransactionType.EXPENSE` only, since a Sankey diagram routes spending, not income or savings deposits/withdrawals. that partial's Personal/Shared toggle drives Alpine's `$store.sharing`, so `build/js/sankey_editor.js` imports and starts Alpine itself and reads the store through that same module-local binding, never `window.Alpine` (the ES-module build of Alpine, unlike its standalone CDN build, never assigns itself to `window` - each page that uses the toggle, dashboard/expenses/sankey alike, has to import+start Alpine on its own). Generation is two-step and explicit, not live/reactive: editing the graph or changing the date range/mode never updates an already-generated chart; `POST /budget/sankey/generate/` recomputes from scratch. `generate()` never blocks on incomplete placement: any catalog node that isn't placed on the canvas is simply excluded from the graph, the same as an explicitly disabled node (`checkbox` on the node) - both are just absent from `enabled_keys`, so an unplaced node needs no special-casing beyond not being in `nodes_config` to begin with. Rendered zero-weight edges/nodes are pruned (`prune_zero_weight`) from that snapshot only, never from the saved graph. A node with real value but literally zero edges (no parent, no child) would otherwise vanish from the chart: d3-sankey computes each node's displayed value purely from its own links, silently zeroing anything with none, discarding whatever value was actually passed in - `_drawChart` (`build/js/sankey_editor.js`) splits the generated result into linked nodes (handed to `d3sankey()` as normal) and isolated ones (drawn separately as plain proportional value bars below the flow diagram, using the real backend-computed value), and the whole render is wrapped in a try/catch that shows an inline error rather than leaving the chart area silently blank on any other failure. Every linked node is also handed a `fixedValue` (d3-sankey's own escape hatch from its default `node.value = max(sum(sourceLinks), sum(targetLinks))` computation) set to our real backend-computed value: a no-op for an ordinary fully-routed node (the two already agree), but required for a node that's also a root and only partially routes its own money onward - it has no incoming links at all and its outgoing links alone sum to less than its true value, so without `fixedValue` d3-sankey would silently undersize its box to just the routed-out portion instead of its full true value. In the generated chart itself (not the editor canvas), every link is stroked in its *target* node's color rather than a flat neutral gray, so a glance at the diagram shows which downstream bucket a flow actually ends up in; a Connector node's bar renders with no on-chart text label since it's pure wiring with no meaning of its own - its name/value is still available on hover via the custom tooltip described below. Chart height is not a flat constant: `_probeColumnCounts` (`build/js/sankey_editor.js`) runs d3-sankey's own layout once at a throwaway height purely to read back each node's real rendered `layer` (not `depth` - see below) and count the most crowded column, then `_drawChart` sizes the SVG to fit that column, so a graph with many nodes stacked in one column no longer gets visually cramped/cut off under a fixed height budget. Reading `node.layer` rather than `node.depth` matters because d3-sankey's default "justify" alignment (`node_modules/d3-sankey/src/align.js`) pushes every *sink* node (no outgoing links) to the same rightmost column regardless of its natural longest-path depth - two leaves reached via a different number of hops from a root can still end up sharing one rendered column, which only `layer` (the post-alignment column) reflects; a naive depth-based or longest-path-from-root estimate undercounts exactly this case. Hovering any node/link in the generated chart, or an edge/anchor in the editor canvas, shows a custom floating tooltip (`_showTooltip`/`_moveTooltip`/`_hideTooltip`, one shared `#sankey-tooltip` div) rather than a native SVG `<title>`, which only appears after the browser's own hover delay. Every node (Tag/Category/Project and Connector alike) has a color override: a "Color" property row (regular nodes) or a small swatch dot next to the diamond (Connector, which has no property rows) opens a floating popover (`_openColorPicker`, 32 preset swatches - 8 validated categorical hues x 4 tone variants each, sourced from the `dataviz` skill's reference palette - plus a hex text field) that sets `n.color` directly - already a plain field on the node saved/loaded via `config_json` and already read back into `nodes_out` by `generate()`, so overriding it needs no backend change to take effect or persist. The in-canvas control panel (top-right overlay, same positioning the zoom +/- buttons always used) is now "the toolbar": `+ Connector node`, Save, Reset, a "Snap to grid" checkbox, then the zoom controls, all grouped in `#sankey-canvas-toolbar` - moved off the page-level bar above the canvas, which now only holds the interaction hints; the Generate button sits below the canvas instead. Snap-to-grid (`_applySnap`, `GRID_SIZE`, on by default) only affects a node or anchor while it's actively being dragged - toggling the checkbox never retroactively moves anything already placed. An edge can carry any number of user-placed "anchors" (`edge.anchors`, a plain `{x, y}` list alongside `source`/`target` - passed through `save_graph`/`generate()` untouched since both only ever read `source`/`target` off an edge dict) purely to shape the drawn line for readability; they have no effect on routing/weights. The drawn line stays one continuous, tangent-continuous curve through every anchor (`_waypointTangents`/`_edgePathFromPoints`: a cubic Bezier segment per gap, each sharing the same tangent direction with its neighbor at every anchor, plus a forced-horizontal tangent at the very first/last point so it still leaves/enters each node's socket flat) rather than a straight-line polyline, so a shaped connection looks as smooth/rounded as an unshaped one. An anchor renders as a small diamond (`_drawAnchor`) on top of its edge, draggable via `_startAnchorDrag` (snap-to-grid applies here too); right-clicking a plain point on an edge inserts a new anchor at the closest segment (`_addAnchorAt`/`_pointToSegmentDistance`, so it lands in shaping order rather than always at the end) and right-clicking an existing anchor does nothing; left-clicking an anchor deletes just that anchor, left-clicking anywhere else on the edge deletes the whole connection (anchors and all). Hovering an anchor turns it red (CSS `:hover`, signaling what a left click there would delete) without recoloring the edge underneath, since the anchor is a separate element drawn on top and captures the hover itself. A "Reset" button (`reset()`, gated behind the shared `window.confirmDialog()` irreversible-action pattern) clears every node and edge from the in-memory graph; like every other edit here, nothing is persisted until the user clicks Save afterward.

Frontend is a hand-rolled SVG canvas editor (`build/js/sankey_editor.js`), following the site's own light/dark theme via the same CSS custom properties as everywhere else (`build/scss/_sankey.scss`) - only each node's header keeps a fixed, vivid per-type accent color (project/category/tag/connector) with white text on it, the same idea as a dashboard card's colored cell, readable regardless of site theme; a bare `<button>` (`.sankey-palette-item`, the Unplaced-palette chips) needs its `color` set explicitly to `var(--text)` or it falls back to the browser's default dark button text, unreadable against `--bg-input`'s dark-mode value. Each Tag/Category/Project node is a colored header bar over a theme-aware body listing its own properties ("Priority"/"Disabled") as labeled rows, plus one blank "connector" row right after the header that carries nothing but the input (left edge) and output (right edge) sockets - deliberately its own row, never lined up with a labeled property, so a wire can never visually read as if it targets a specific value (`_socketPos` always returns the connector row's center, regardless of a node's actual height) - **except** a Connector *node* (`_drawConnectorNode`), which skips this box entirely and is instead a small unlabeled diamond (a rotated square, `CONNECTOR_SIZE`) with just its two sockets (at the diamond's left/right tips) and a small "×" to delete it: no header, no title, no Priority/Disabled rows, since a Connector's own priority is structurally irrelevant (as a child it's always evaluated last regardless of its priority number, see `build_children_order`) and it can never be disabled - the diamond shape itself is what visually says "this is pure wiring, not a real node." Wiring is click-drag-drop from either socket, with a live dashed "noodle" path following the cursor until it's dropped on another node (`_startConnect`/`_updateTempLine`/`_endConnect`). Two nodes far enough apart that they can't both fit on screen at once would otherwise be impossible to wire together without letting go to pan manually first: while a connection is being dragged, the cursor nearing the viewport's edge auto-pans the canvas toward it (`_startAutoPanLoop`/`_autoPanTick`/`_stopAutoPanLoop`, `AUTO_PAN_EDGE`/`AUTO_PAN_SPEED`), continuously via `requestAnimationFrame` rather than only on `mousemove` so it keeps scrolling even with the cursor held still right at the edge. Each tick calls `_applyTransform()` (just the `<g>` transform attribute) rather than the full `render()`, both because a pan/zoom change alone never needs nodes/edges redrawn (they're already positioned relative to that transform) and because `render()` clears `this.g`'s children, which would delete the live temp connecting line mid-drag; `_updateTempLine` is re-run every tick so the noodle keeps tracking the (screen-fixed, world-shifting) cursor position as the pan changes underneath it. New nodes placed via the palette or `+ Connector node` similarly spawn inside the current viewport (`_nextSpawnPos`/`_viewportWorldRect`, a small grid sized to what's visible, cascading with a diagonal offset once a heavily zoomed-in viewport's grid runs out of slots) rather than at a fixed canvas-origin position that could be far outside a panned-away view. Canvas navigation: scrolling empty canvas zooms centered on the cursor, not the origin (`_onCanvasWheel`/`_zoomAt` solves for the pan that keeps the world point under the cursor fixed on screen before/after the zoom change); the zoom is multiplicative and proportional to the wheel event's actual `deltaY` (`ZOOM_WHEEL_SENSITIVITY`), not a fixed step per event - a trackpad fires many small-`deltaY` events per gesture where a mouse wheel fires few large ones, so a fixed-step-per-event design (tried first) made trackpad scrolling zoom far too aggressively; scaling by `deltaY` keeps the total zoom change proportional to total scroll distance regardless of event count. The −/+ buttons (`_zoomBy`, a fixed multiplicative factor) live inside the canvas viewport itself, absolutely positioned top-right (`.sankey-zoom-group`, `.sankey-canvas-wrap` as its `position: relative` anchor) rather than in the toolbar above, since that's where a zoom control is expected to act on the thing it controls; both wheel and button zoom funnel through the same `_zoomAt`, just anchored at the cursor vs. the canvas's own center. Click-dragging empty canvas pans, with no position limits (`_startPan`/`_endPan`, gated the same way node-drag/connect already are - every interactive element stops propagation on its own mousedown, so a pan only ever starts from a genuine background click); `#sankey-canvas` sets `user-select: none` so a click-drag pan never highlights node/label text along the way, which a plain click-and-drag gesture would otherwise trigger as browser text selection. The toolbar's hint text is one block per instruction (`.sankey-hint` forces its own flex row via `flex-basis:100%`, with each instruction its own `<div>` inside it) rather than one run-on line, so it doesn't wrap mid-sentence. The Unplaced palette sits in its own full-width bar above the canvas (not a side rail) so the canvas gets the page's full width; the page itself caps at the dashboard's own 1200px `main.app-main` max-width. The generated chart itself is laid out with `d3-sankey` (bundled locally same as everywhere else).

**Participant overlay auto-matching on expense creation** (`budget/services.py::create_participant_overlays`, called from `budget/views/expenses.py` and `generate_scheduled_expenses.py`): when a real-user participant has no overlay yet, a title-matching **category** is auto-applied unconditionally (a wrong category match is just wrong -- easy to notice and fix), but a title-matching **tag** is only auto-applied when the participant and the expense owner are in the same onboarding-complete Catalog Partnership (`budget/services.py::_same_catalog_partnership`), where their tag catalogs are actually guaranteed to be the same set. Unrelated feusers never get tags auto-matched by title: a coincidental match ("Restaurant" vs "Restaurante") would assign one plausible-looking tag while silently dropping every other tag the expense should have gotten, and -- because that makes the overlay non-empty -- the expense would stop showing up on the Unclassified Expenses page above even though it's still missing most of its real tags.

**Dashboard cards** (`budget/dashboard_cards.py`): stored as `DashboardCard` with `yaml_config` only; all layout in YAML `positioning:` block. Types: `cell`, `bar-chart`, `pie-chart`, `list`, `line-chart`, `gauge`. API uses session auth (not Bearer): `GET/POST /budget/dashboard/cards/`, `PATCH/DELETE /budget/dashboard/cards/<id>/`. AI card assist (`budget/dashboard_card_ai.py`, `POST /budget/dashboard/cards/ai/`): generates/edits a card's YAML from a free-text prompt; system prompt is built live from `docs/src/docs/user-manual/dashboard/` (all child pages) plus the user's catalog and their other cards' YAML, so it stays in sync with the docs automatically. Gated by `ai_smart_create_available` (context processor) and per-user trial exhaustion; result only fills the YAML editor, never auto-saves.

**Notification classes** (ordered): `"" < soon < tomorrow < today < late < settled`; each sent at most once per expense.

**Double-submit guard** (`templates/base.html`): a global `document` `submit` listener disables every submit button in a form (`.is-loading` class, styled in `_buttons.scss`) the moment a submit event isn't cancelled, so a stray second click can't re-fire the same create/save action before the page navigates away. Applies automatically to any plain form; pages that intercept `submit` themselves (buddy consent AJAX, the date-range-warning confirm dialogs in `expense_form.html`/`express_creation.html`) call `e.preventDefault()` first, which the guard checks (`e.defaultPrevented`) and skips, leaving those flows to lock the button on their own eventual real submit. No per-page wiring needed for new create/save buttons.

**Toast stack** (`templates/partials/_toast_stack.html`, included once by `templates/base.html`; `.toast-stack`/`.toast` in `_misc.scss`): the single, sitewide rendering path for every transient flash notification, fixed bottom-right (`position: fixed`, `column-reverse` so a new toast slots in above the corner and pushes older ones up) so appearing/disappearing never reflows page content. Two ways in: `django.contrib.messages` entries (`messages.success`/`.error`/etc., any view) are rendered server-side into the stack on page load, one `.toast toast-{{ message.tags }}` per message; `window.showToast(message, tag='success')` (defined in `base.html`, alongside `window.confirmDialog`) appends one client-side for an AJAX action that doesn't reload the page. Both paths share the same auto-dismiss timer (5s) and a manual "×" close button, wired by the same `initToast()` helper. No per-page wiring needed -- do not hand-roll a page-local flash/toast element for a new feature; call `window.showToast` (JS) or `messages.success()` (server-rendered) instead. Tag classes (`toast-info`/`-success`/`-warning`/-`error`) reuse the same color-mix recipe as `.buddy-flash`'s tag variants (still used on their own for a couple of static, non-dismissing warning boxes, e.g. `kick_dummy_confirm.html`'s "Outstanding balance" notice -- those aren't flash messages and stay put).

## Demo users (`is_demo=True`)

A demo user is a shared public account anyone can log into. Every restriction on a demo user must satisfy two hard rules:

1. **No interaction with real users.** A demo user must never be able to send emails, invitations, partnership requests, or any other out-of-band contact to a real account. Real users must equally be unable to pull a demo account into their social graph (buddy, project member, partner).
2. **No sabotage of the shared demo experience.** A demo user must never be able to perform an action that degrades the demo for the next visitor: they cannot change their own name, email, or password; cannot delete the account; cannot set up 2FA; cannot generate an API key.

What demo users **can** do: change currency, financial month settings, unspent allowance action, create expenses, use AI express entry (subject to `special_ai_trial_budget`).

The demo banner (shown at every login, must be accepted) and all server-side blocks are enforced regardless of `ENABLE_DEMO_USERS`. That flag only gates login access and the landing-page advert. `reset_demo_user` (run by `run_cron`) deletes all `is_demo=True` users and recreates a fresh "Dean Demo" account once the last one has been inactive for a week.

When adding any new feature: if it sends email, modifies another user's data, or lets a user meaningfully alter their own identity/credentials, block it for demo users — both in the view (redirect/403) and in the UI (disabled/hidden).

## Transport / TLS
This app is ALWAYS deployed behind a reverse proxy that terminates TLS and forwards
plain HTTP to Gunicorn. The app itself expects HTTP and does NOT enforce HTTPS in any
way: it never redirects HTTP->HTTPS, never emits HSTS, and never inspects
`X-Forwarded-Proto`. HTTP->HTTPS redirection and HSTS belong on the proxy, not here.
Do not add `SECURE_SSL_REDIRECT`, `SECURE_HSTS_*`, or `SECURE_PROXY_SSL_HEADER`:
enabling app-side HTTPS redirect behind an SSL-terminating proxy causes an infinite
301 redirect loop. When `DEBUG` is off, the only transport hardening the app applies is
marking the session and CSRF cookies `Secure` (safe because the public edge is HTTPS).
