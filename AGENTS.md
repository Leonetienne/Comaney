# Comaney: Agent Reference

## Rules
- Never use em-dash '—'; use ':', ';', or rewrite
- Never commit, push, or publish
- Only analyze, modify, create, or delete files and run commands
- Updating a feature: keep CLAUDE.md, AGENTS.md, docs/src/, and the requirements in specs/ in sync (format: specs/README.md)
- Requirements are mandatory: see "Requirements (specs/)" below
- New functional features or fixes: must add tests
- Always code in a way a human can maintain it!
- Use best practices, Don't repeat yourself (DRY), clear architecture
- Never load anything from the internet after deployment, except calls to the configured AI provider and YubiKey OTP validation server calls
- All assets (fonts, images, scripts, libraries, etc.) must be served locally: either a plain JS file under `build/js/`/`static/` or a package installed with yarn (preferred) and bundled via esbuild; never a `<script src="https://...">`/CDN reference

## Requirements (specs/)
`specs/` is the single requirements database for the whole system and must always describe the code as it is. Format and conventions: `specs/README.md` (ISO/IEC/IEEE 29148 structure, EARS sentences, OpenFastTrack item IDs).
- Every change that adds, changes, or removes observable behaviour updates the affected requirements in `specs/requirements/` in the same change. No feature or fix is done until its requirements match the code.
- New feature area: add a `feat~...~1` item to `specs/features.md` (with `Needs: req`) plus its requirements file.
- Changed meaning of a requirement: bump its revision (`~1` -> `~2`). Removed behaviour: delete the item. Never reuse an ID for something else.
- Every `req` item covers exactly one `feat` item via `Covers:`.
- `specs/` is a long-term archive of how the app is supposed to behave, not a plan for implementing a feature. Never write requirements for unbuilt behaviour there; they go in together with the code.
- Plans for unbuilt features live in an untracked `<feature>-plan.md` in the repo root (e.g. `mcp-plan.md`). Once built, their decisions move into `specs/` and the plan file is deleted. Never create loose `*-spec.md` files.

## Auth
- Custom `FeUser` model, not `django.contrib.auth.User`
- Session key: `request.session["feuser_id"]`; load via `_get_session_feuser(request)`
- Never use `request.user`, `login()`, or `@login_required`
- REST API (`/api/v2/`): Bearer token -> `FeUser.api_key` (limited by `FeUser.api_key_permissions`), or the browser session with CSRF (full access)
- MCP (`/mcp`): Bearer agent key -> `mcp_server.AgentKey` (SHA-256 hash lookup); never the API key, never for demo users

## Glossary

- **feuser**: an app user, backed by the custom `FeUser` model (not `django.contrib.auth.User`). Session key `request.session["feuser_id"]`.
- **expense**: a single spending record (`budget.Expense`). Always has exactly one `owning_feuser` (the "owner").
- **owner / owning expense**: the feuser recorded as `Expense.owning_feuser`. Only the owner's own `category`/`tags` fields on the `Expense` row itself count as "their" classification of it.
- **foreign expense**: an expense the current feuser did not create (is not the `owning_feuser`) but is a **participant** on, via a `BuddySpending` row.
- **participant**: a feuser (or offline dummy) with a `BuddySpending` row against an expense they don't own, representing their share of that spend.
- **expense overlay** (`ExpenseDataOverlay`): a participant's personal category, tags, and note for a foreign expense, stored separately from the expense itself (one row per `(expense, feuser)`). Lets each participant classify a shared expense their own way without affecting the owner's or other participants' classification. Never stored empty; deleted instead of zeroed (see `budget/services.py::upsert_overlay`).
- **category**: a single label (`budget.Category`) an expense (or overlay) can have. Owned per-feuser; one category per expense.
- **tag(s)**: zero or more labels (`budget.Tag`) an expense (or overlay) can have. Owned per-feuser; a plain many-to-many relation.
- **contact**: another feuser (or offline dummy) you split expenses with directly, outside of any project; formerly "direct buddy". The UI, docs, specs and direct-buddy code use "contact" (`ContactLink`, `ContactInvite`, `contacts`, `/buddies/contacts/`). The `buddies` app, `BuddySpending`, `Buddy*Service` and other generic sharing code keep the old name.
- **project**: a shared group of members (`buddies.Project`) that expenses can belong to; formerly called "Buddy Group".
- **project member**: a feuser or dummy belonging to a project (`buddies.ProjectMember`).
- **partner**: another feuser in the same Catalog Partnership as you (shared category/tag catalog mapping) - distinct from "contact".
- **dummy / offline member / offline contact**: a non-feuser participant (`buddies.DummyUser`) standing in for someone without an account.
- **own AI settings** (`FeUser.ai_user_config`): a feuser's own credentials/options for the AI provider, one JSON entry per provider (`{"claude": {"api_key": "..."}}`); only the active provider's entry is ever used. Replaced the former `anthropic_api_key` column.
- **settlement**: an expense with `is_buddies_settlement=True` recording a debt payoff between two participants, not a real spend.

## Key conventions

**Projects** (`buddies/`): renamed from "Buddy Groups"; DB aliases still exist. `Expense.project` FK links to project. Call `project.update_lastmod()` on every mutation. The project page has three tabs, each its own view/URL/template sharing the `buddies/_project_tabs_header.html` partial (hero, tab nav) and a `_project_common_context(feuser, project, active_tab)` helper (`buddies/views/projects.py`) for the identity/membership/breakdown context all three need: **Expense list** (`project_detail`, default, `/projects/<id>/`) has the total-spending header, pending items, settle-up tools ("Pay someone back", "Clear everything at once"), and the expense list/filters; **Insights** (`project_insights`, `/projects/<id>/insights/`) has the balances + D3 debt graphs, spending-breakdown pie chart, spending-over-time line chart, and spending-by-tag bar chart, laid out via `.insights-grid`/`.insights-card` (2-3 col grid, collapses to 1 col under `560px`, see `_buddies.scss`); **Settings** (`project_settings`, `/projects/<id>/settings/`, admin-focused, renamed from "Manage") has the member list and admin-only actions; its "Add members" block (`build/js/project_member_add.js`, `_member_add.scss`) offers the admin's contacts as a combobox under "Invite by email" (server-rendered hidden `.contact-suggestion` items reusing `partials/_avatar.html`, existing members never suggested), shows a contact/not-a-contact hint for the typed email, and warns (plus OK/Cancel `confirmDialog` on submit) when an offline-member name looks like an email (loose `EMAIL_LIKE` regex) or matches a contact; `currentWarning()` returns at most one of these (email first), so hint and dialog can never double up. Both checks go through the single `matchingContacts()` (case-insensitive substring of first name, last name or email); hints sit in reserved `.input-hint` lines (`--multiline` for the wrapping warning) so they never shift the layout. Solo projects hide the debt graph, pie chart, and settlement sections regardless of tab. Archived projects block mutations except confirming in-flight settlements. `Project.permission_laxity` (`PERMISSION_LAXITY_ADMIN_ONLY=0` default, `PERMISSION_LAXITY_MEMBERS=1`) governs who may edit name/description/picture/AI preprompt: gate all four via `project.can_edit_details(feuser)` (admin always true; other members only when laxity is `MEMBERS`). Admin sets it via a dropdown on the Settings tab (`project_set_permission_laxity` view, admin-only). Everything else (invites, transfer, archive, delete) stays admin-only.

**API and MCP** (`api/`, `mcp_server/`; requirements `specs/requirements/api.md`, `mcp.md`): every API action is defined once as an `Operation` in `api/registry.py` via `@operation(name, concern=, access=READ|WRITE, method=, path=, description=, params=<JSON schema properties>, required=, destructive=, status=)`, with the handler `(ctx, args)` in the concern's module under `api/operations/`. `api/rest.py` builds the `/api/v2/` routes from the registry; `mcp_server/endpoint.py` builds the MCP tools from it, filtered by the agent key's permissions (`AgentKey.permissions`, `{concern: {"read", "write"}}`, write implies read). The REST API key has the same permissions (`FeUser.api_key_permissions`, default full access, kept when the key is revoked), enforced in `api/rest.py::dispatch` for Bearer callers only (403); both keys read them through `api/permissions.py::KeyAccess` (`key.access`, `feuser.api_key_access`) and share one Restrict panel partial (`feusers/partials/_key_permissions.html`). A new API action is one `@operation` and is then automatically a REST route, an MCP tool, a row under its concern in both Restrict panels, and must get a row in `docs/src/docs/user-manual/api-access.md` (enforced by `tests/e2e/api/test_api_docs.py`) and the Postman collection. Handlers hold no business logic: they validate (reusing the web forms via `common.form_data`/`form_errors`) and call the same service functions the web views call: `budget/expense_service.py` (create/edit with approval reset, delete, clone, bulk, overlays; `update_expense` snapshots the stored row because form validation already wrote the new values onto the instance), `budget/scheduled_service.py`, `budget/catalog_service.py` (partnership sync), `budget/dashboard_service.py`, `feusers/settings_service.py`, and `buddies/services/{project_actions,contact_actions,approvals,settlement_actions,partnership_actions}.py`; a view or handler never re-implements those rules. Project reads go through the same breakdown as the project pages: `projects_overview` uses `BuddyQueryService.get_group_full_breakdown` plus `project_expense_flows` (also behind the Insights tab's "Expense flows" graph), `settlements_list` uses `settlements_visible_to`/`settlement_parties`. Errors are `OpError(message, status)`; two-step destructive actions (bulk delete, partnership onboarding) issue a signed token from `api/operations/confirm.py`, bound to feuser, agent key and a fingerprint of the previewed state. The MCP server is stateless JSON-RPC (`mcp_server/protocol.py`, Django-free and unit-tested), sends `INSTRUCTIONS` that point the agent to the user manual, and gives every key `docs_search`/`docs_read` over `docs/src/docs/user-manual/` (`mcp_server/docs.py`) plus the manual pages as resources. There is no tool for account creation/deletion, email, password, second factors, API or agent keys, or own AI settings.

**Achim Archive**: removing a DummyUser merges their history into a special `is_archive=True` dummy instead of deleting it. Service: `BuddyArchiveService` in `buddies/services/archive.py`.

**Real and offline conversion**: removing a project member (`ProjectService.remove_member`) puts a new offline member in their place; the admin, as owner of an offline-paid expense, always holds a row (0% if missing). Removing a contact (`BuddyLifecycleService.kick_actual`) copies, so the two share no expense afterwards: each side gets an own copy of what the other paid, then an offline contact replaces the other in its own expenses. Merging an offline entry into a real user is always `BuddyArchiveService.merge_dummy_into_feuser` (contacts, projects, project self-merge); notes stay untouched. Sending and accepting a contact merge request warns, via `confirmDialog`'s optional `detail` node, with a copyable list of contact expenses of equal title and amount on both sides (`BuddyQueryService.offline_record_overlaps`/`merge_invite_overlaps`, `templates/partials/_merge_overlap_list.html`, `merge_dummy_js.html`).

**Participant approvals** (`BuddySpending.approval_state`/`consent_set_at`, the Check/X consent shown per-participant): applies equally to contact and project expenses. When the owner edits a shared expense and changes the title, value, participants, or any share, all participants' approvals reset (state -> `APPROVAL_NEUTRAL`, `consent_set_at` -> `None`). Editing only unrelated fields (payee, note, category, date) preserves approvals. The "your approval was reset" note in the update email goes only to participants who had actually approved beforehand (not neutral/rejected). `set_buddy_spendings` always deletes/recreates rows (fresh = reset); `expense_edit` decides reset-vs-preserve via `BuddyExpenseService.spend_signature`/`snapshot_approvals`/`restore_approvals`/`reset_participant_approvals`, and passes `reset_participant_pks` (the previously-approved pks) into `BuddyEmailService.notify_expense_updated`.

**Contact auto-accept trust** (`buddies/services/trust.py::BuddyTrustService`): a feuser B can opt, per contact A, to "Automatically accept expenses and settlements recorded by A" (toggle "Automatically accept expenses, settlements and project invitations from A" in Contacts, `set_auto_accept` view, `POST /buddies/link/<id>/auto-accept/`, OK/Cancel `confirmDialog` on enable). Stored per direction on `ContactLink` (`user_a_auto_accepts_from_b`/`user_b_auto_accepts_from_a`, via `link.auto_accepts(truster)`/`set_auto_accepts`), so it only exists between contacts (also inside projects, but only when A and B are contacts too) and disappears with the link. "Recorded by A" means `Expense.initiated_by_feuser == A`: the feuser whose action last made the expense need someone else's confirmation. Every such action calls `BuddyTrustService.record_action(expense, actor)` right after it (web create/edit/clone, AI Express, scheduled generation and apply-to-existing, direct/individual-group/group-wide settlements, pending settlement edits), which stamps `initiated_by_feuser` and, for each involved feuser who trusts the actor, accepts: "Did you pay for this?" (`approve_expense`), settlement receipt as creditor (`BuddyLifecycleService.confirm_settlement`, shared with the manual confirm view, books the "Settlement received" income), and the truster's neutral participant approval indicator (-> approved, never overriding a rejection). It mutates the expense in place, so call sites send the regular approval/confirmation request only `if not expense.buddy_approved` afterwards; a trusting truster instead gets an info-only email (`send_expense_auto_accepted` under `expense_assignments`, `send_settlement_auto_accepted` under `settlements`, both linking to Contacts). The trust also covers project invitations: when admin A invites a trusting B, `ProjectService.invite_member` returns `("auto_joined", invitee)` and `BuddyTrustService.accept_project_invite` joins B through `ProjectService.join_via_invite` (the same conclusion the manual `accept_group_invite` uses, with `notify_inviter=False`), emailing B `send_project_invite_auto_accepted` (`group_activity`) instead of the invitation. Merge and partnership requests are deliberately not covered. Enabling the trust also accepts, silently, every pending entry initiated by A (`pending_from`) and joins every open, unexpired invitation from A (`pending_invites_from`); `set_auto_accept` returns an `AutoAcceptResult(entries, projects)`. Expenses in archived projects are never touched and archived projects are never joined. There is deliberately no backfill of `initiated_by_feuser`: rows from before the field existed stay manual. A sees an "Accepts your entries automatically" pill next to B in their own contact list. The expense form and AI Express also know it: `BuddyTrustService.trusters_of(actor)` feeds an `autoAccepts` flag into each feuser entry of `_buddy_context()`'s `contacts` and `projects_data_for_expense_form`'s members, so picking a trusting B as upfront payer shows "B accepts your entries automatically, so no approval is needed" instead of the "requires their approval" warning, in both the payer notice and the submit confirm dialog (`buddy_expense.js::payerApprovalText`, and `express_creation.html`'s `updateNotice`). The AI catalog never sees this flag. Data exports (account export and contact summary export, both via `BuddyExportService.write_contact_csvs`) list the trust per contact in `contacts.csv` as `i_auto_accept_theirs`/`they_auto_accept_mine` (empty for offline contacts).

**Settlements**: debtor creates with `settled=True, buddy_approved=False`; balance clears only when creditor confirms (`buddy_approved=True`). Settlement expenses must never appear in "Did you pay for this?" (`pending_as_expense_owner` filters `settled=False`).

**Second factors** (`feusers/second_factor_registry.py`): TOTP, WebAuthn, Email, and YubiKey OTP are all `SecondFactorAuth` subclasses registered via `register_factor_type(FactorType(...))`; login, removal, profile, rename, and test views drive entirely off this registry (`factor_type_for`, `get_all_factors`, `method_key_of`) and never branch on a method name, so a further method needs only a model + one registration call. Login-time verification for a given method is dispatched through `_LOGIN_VERIFIERS` (`feusers/views/twofa.py`) rather than inline branching; `factor_test` (profile "Test" button, `feusers/factor_test.html`) reuses that same dispatch table and the registry's `challenge_template` partial to let a user try one specific factor in isolation (e.g. tell same-named security keys apart) without touching login/session state. `factor_rename` is a small JSON endpoint following the Categories & Tags inline-rename pattern (`.ct-name`/`.ct-name-input`, click to edit, POST on commit). The profile page's "Add new second factor" is a single `.method-dropdown` toggle (same component as the login/removal "try a different method" menus) unrolling one item per available method, rather than a separate button per method. No setup view renders its own "<method> added" confirmation screen: `second_factor_service.finish_setup(request, feuser, first)` is the shared conclusion for `totp_setup`/`webauthn_setup`/`email_factor_setup`/`yubikey_setup` alike, flashing a fresh recovery code into the session (only when `first`) and redirecting to `profile?success=2fa#section-2fa`, where `profile.html` pops and renders it once. `account_export` (`feusers/views/account.py`) includes `second_factors.csv` (method, label, is_primary, created_at via the same registry, for GDPR access requests) but deliberately never the underlying secret/credential of any method - that would hand out a working authentication bypass instead of personal data. It also includes `sankey_graph.json` (the feuser's `SankeyGraph.config_json` verbatim), added only when a graph has actually been saved (`feuser.sankey_graph` is a `OneToOneField`, absent for most feusers).

**YubiKey OTP second factor** (`feusers/yubico_otp_service.py`, `feusers/views/yubikey.py`): implements the [Yubico OTP protocol](https://developers.yubico.com/OTP/OTP_Walk-Through.html) - a signed HTTP round trip to a Yubico-protocol validation server, not local math, since there is no secret to check a code against locally. Gated instance-wide on `YUBICO_CLIENT_ID` and `YUBICO_SECRET_KEY` both being set (`yubikey_available` computed inline the same way as `webauthn_available`/`email_2fa_available`, in `profile`'s view context and `yubikey_setup`'s own guard); `YUBICO_SERVER` defaults to Yubico's own `https://api.yubico.com` if unset, but can point at a self-hosted validation server instead. `YubikeyFactor.public_id` (the fixed first 12 characters of every OTP a given physical key ever produces) is what a factor is stored and matched against - `unique=True` the same way `WebAuthnFactor.credential_id` is, since one physical key can only meaningfully be registered once across the whole instance; `yubikey_setup` checks for an existing row with that `public_id` before creating a new one and surfaces a plain "already registered" error rather than a DB integrity error. `verify_otp()`'s HTTP transport is dependency-injected (`fetch=`) purely so the signing/response-verification protocol itself is unit-testable without a network call; only its default implementation touches the network. There is no local replay/counter tracking (contrast `WebAuthnFactor.sign_count`): the validation server itself rejects a replayed OTP (`status=REPLAYED_OTP`), which `verify_otp()` treats the same as any other non-OK status.

**Email second factor** (`feusers/email_factor_service.py`, `feusers/views/email_factor.py`): `EmailFactor` is a regular TOTP secret (`feusers/models/second_factor.py`), but the code is delivered to the feuser's own inbox on request rather than read off a local authenticator app; it uses a 5-minute step (`CODE_INTERVAL`) instead of the usual 30s so the code survives email delivery lag, and the code itself is never stored anywhere (DB or cache) since pyotp recomputes it from the persisted secret + current time on every send and every verify. Capped at one `EmailFactor` per feuser (a second would always target the same address), which lets the single ajax send-code endpoint (`email_factor_send_code`) resolve its target purely from server-side session state (authenticated feuser's own factor, a mid-setup session secret, or the post-password-check pending-login factor) with zero client-supplied ids, closing off any "email an arbitrary user" abuse path. Sends are throttled via `email_factor_service.request_send` (a 60s cooldown plus a 10/hour hard cap, both via the generalized `rate_limit.is_limited`/`record_failure`, which now take optional `window`/`max_attempts` kwargs alongside their original login/TOTP brute-force defaults); the throttle bucket key is `f"{feuser_pk}:{purpose}"`, not just the pk. `purpose` is one of `"setup"` (confirming a not-yet-registered factor), `"login"` (an in-progress, not-yet-authenticated login), or `"confirm"` (an authenticated feuser acting on their own already-registered factor: `factor_test`, or a removal/recovery-regen confirm step) - `email_factor_send_code` picks it per-request based purely on session state, same as it picks the send target. Splitting these out means testing the method, or setting it up, can never block an actual login, and vice versa; it's safe because a feuser is only ever in one purpose "slot" for real - once a factor is persisted `"setup"` is unreachable for that account forever, and `"confirm"` requires already being fully authenticated, i.e. having already passed the very `"login"` gate it can't then block. On top of that, `_verify_email_login` (`feusers/views/twofa.py`, the sole dispatch target for the `"email"` key in `_LOGIN_VERIFIERS`) calls `email_factor_service.clear_login_send_throttle` the moment a code check succeeds - in *any* of those three contexts - since correctly entering the current code already proves the owner can read their inbox, so there's no reason to leave the `"login"` bucket engaged afterward (e.g. logging out and immediately signing back in). `request_send`'s `purpose` also picks between two email templates/subjects (`"setup"` uses `emails/second_factor_email_code_setup.html`; everything else falls back to the `"login"`-styled `emails/second_factor_email_code.html`, via `_TEMPLATES.get(purpose, _DEFAULT_TEMPLATE)`): telling the user they're "finishing signing in" would be misleading while they're still confirming a not-yet-registered factor. Hitting the cooldown is surfaced to the frontend as a `reason: "cooldown"` field (vs `"hourly_cap"`) so `_email_send_js.html` can show it as a reassuring "a code was already sent, check your inbox" note instead of an alarming error - the cooldown by definition means a code went out within the last 60s, well inside its 5-minute validity. The challenge/setup templates auto-trigger a send on load and show a client-side-timed "Resend code" link (`.link-button`, `feusers/templates/feusers/partials/_email_send_js.html`); availability is gated instance-wide by `email_2fa_available` (`not settings.DISABLE_EMAILING`, `feusers/context_processors.py`), same pattern as `webauthn_available`.

**Scheduled expenses** (`budget/management/commands/generate_scheduled_expenses.py`): materialization runs on the cron and synchronously on every `ScheduledExpense` create/edit. Dedup key is `Expense.scheduled_occurrence_date` (immutable, never `date_due`, never shown in any form/API). `ScheduledExpense.last_run` (financial year) gates a schedule to materialize at most once per year; `--year` bypasses the gate. `repeat_every_factor`/`repeat_every_unit` (Gate A) and `repeat_base_date`/`end_on` (Gate B) are locked on edit behind `confirm_modify_schedule` / `confirm_modify_schedule_window` (checkbox in the web form, boolean in the API PATCH body); unconfirmed changes to those fields are silently discarded server-side. Confirmed Gate A wipes and regenerates every current-year expense for the schedule (including settled ones); confirmed Gate B forces a regeneration pass that prunes now-out-of-window expenses and adds newly in-window ones, both by resetting `last_run = None` before calling `_generate_and_notify`.

**Migrations**: `./venv/bin/python3 manage.py makemigrations` to generate, then `docker-compose exec web python manage.py migrate` to apply.

**Query parser** (`budget/query_parser.py`): `apply_query(qs, query_str)`. Filters: `type=`, `settled=`, `deactivated=`, `value` (comparisons), `date` (dd.mm.yyyy / mm/dd/yyyy / yyyy-mm-dd, magic: `today`, `cur_week_start`, `cur_week_end`), `cat=`, `tag=`, `payee=`, `project=`, free-text, `||` OR, `()` grouping, `!` NOT. The "own tags/category if owner, else feuser's own `ExpenseDataOverlay`, never the foreign owner's" visibility rule for `tag=`/`cat=` exists in four shapes that must stay in sync: `_tag_q`/`_cat_q` (a Q filter for one known value), `query_parser.visible_tag_titles` (a per-expense Python check, used by the project tag bar chart in `buddies/views/projects.py`), `dashboard_cards.py`'s `_compute_chart` (a bulk ORM GROUP BY for dashboard bar/pie cards in shared mode), and `budget/unclassified.py` (the Unclassified Expenses page's own row-building, which additionally treats a missing/empty overlay as "no category, no tags" rather than just skipping it) - the middle two also scope the per-tag/category *amount* to the feuser's own `BuddySpending` share for expenses they don't own, never the full expense value.

**AI calling framework** (`budget/ai_service.py` + `ai_providers/`): `AIService` is the single entry point for every AI feature in the app -- express expense creation, dashboard card AI assist (`budget/dashboard_card_ai.py`), Catalog Partnership tag/category mapping (`buddies/services/partnership_ai.py`), and Unclassified Expenses AI-solve (`budget/unclassified_ai.py`). the base builds the body (`model`, `messages`, `max_tokens` only; all system parts joined into one system message; images as `image_url` data URIs), sends `Authorization: Bearer` only when an api key is set (none at all otherwise), tolerates a missing `usage` (cost 0, logged once per process) and list-of-parts content, maps 401/403 auth, 402 and billing-worded 429 billing, other 429/5xx/timeouts/connection errors transient, unexpected bodies invalid; **Unclassified Expenses** (`budget/unclassified.py`, `budget/unclassified_ai.py`, `budget/views/unclassified.py`, `/budget/unclassified/`): surfaces every expense missing a category and/or tags, from the current feuser's own point of view. Settlement expenses (`is_buddies_settlement=True`) are never unclassified, and neither are savings deposits/withdrawals (`EXCLUDED_TYPES = [TransactionType.SAVINGS_DEPOSIT, TransactionType.SAVINGS_WITHDRAWAL]`, applied everywhere `is_buddies_settlement=False` is) -- moving money between your own accounts isn't the kind of spend a category/tag classifies meaningfully; archived-project expenses still are (archiving blocks mutating the expense, not classifying it). `budget/unclassified.py::resolve_expense_kind`/`_build_row` are the single place that builds a "row" (own-vs-overlay resolved category/tags + a `problem` string, one of `"Category missing"`/`"Tags missing"`/`"Category and Tags missing"`/`None`), reused by the list page, the single-row save, the bulk save, and the AI-solve endpoint so they can never disagree on what a row looks like. A 402 (AI budget/trial exhausted, enforced by `AIService.__init__` itself -- the same framework-level guard every AI feature gets, verified to block before any provider call is made) sets `aiUnavailable` client-side, hiding every AI button on the page without touching already-applied pending changes. **Sankey Studio** (`budget/sankey_service.py`, `budget/sankey_generation.py`, `budget/views/sankey.py`, `budget/models/sankey.py`, `/budget/sankey/`; requirements in `specs/requirements/sankey.md`): gated behind `FeUser.enable_early_access` ("Enable early access features", default `False`, profile "Early access" card, `feusers/forms.py::EarlyAccessSettingsForm`) - the sidebar link is hidden via `sankey_studio_available` (`feusers/context_processors.py`), and all three views (`sankey_studio`, `sankey_save_api`, `sankey_generate_api`) re-check `feuser.enable_early_access` directly (not the context processor, to avoid a redundant query) and refuse direct-URL access: the page view redirects to the dashboard, the two POST APIs return a 404 JSON error. This is the only early-access-gated feature so far; a future one should reuse the same `enable_early_access` flag rather than adding a new per-feature setting. Lets a feuser arrange their own Tags, Categories, and Projects (one shared pool of "nodes") into a directed flow graph and generate a Sankey chart from real expense data. There is no AI-assisted graph suggestion for this feature (tried once, removed: the AI routinely proposed nonsensical topology, e.g. tags as source/"input" nodes rather than downstream targets) - the graph is built by hand only. One `SankeyGraph` per feuser (`config_json`: `{"nodes": {...}, "edges": [...]}`, node keys `"tag:<pk>"`/`"category:<pk>"`/`"project:<pk>"`/`"connector:<token>"`), extended incrementally rather than rebuilt: a newly-created catalog entity just appears in the editor's "unplaced" palette, never auto-inserted. `budget/sankey_service.py` is the pure, Django-free routing algorithm (unit-tested in `tests/unit/test_sankey_service.py`): edges must form a DAG (`topological_order`/`CycleError`, `would_create_cycle` for live edit-time rejection), and every node's priority is a single node-owned integer (not per-edge/per-parent, settable only via its own number input field, never by scrolling the node - scroll-to-adjust was tried and dropped, it collided with scroll-to-zoom too easily) used to sort whichever siblings a given parent happens to have, tie-broken by origin type (project > category > tag) then alphabetically (`build_children_order`). Weights are computed by `partition_flow` as a top-down, first-match-wins partition, not independent per-edge sums: independent sums would double-count an expense that matches two sibling children (e.g. tagged both "Food" and "Drinks"). There is no "Other"/catch-all node type and nothing is ever auto-injected: a node whose wired real children don't collectively claim 100% of its inflow simply keeps the rest for itself, always, for every node - `node_totals` (see `partition_flow`) is computed as a node's full inflow *before* any distribution to children, so it already reflects whatever a node kept regardless of whether any of that inflow went anywhere. One mechanism covers all three of "keep everything" (no wired child matches anything, functions like a true leaf despite the drawn edges), "pass everything along" (children between them claim it all), and "keep some, pass some" (children claim part of it) - none of the three needs any special setting; `sum(inflow) == sum(outflow)` is therefore not a general invariant, only something that happens to hold when a node's children cover its whole inflow. A `connector:<token>` node (`"+ Connector node"` in the toolbar, `CATCH_ALL_TYPES` in both `sankey_service.py` and the JS) is a plain wiring shortcut with no meaning of its own, for collapsing an M-node fan-in/N-node fan-out into M+N edges through one shared hub instead of M*N direct edges: as a *child*, it's always evaluated last regardless of its own priority number and claims whatever its siblings didn't (it has no expense data of its own to match against, so `matches[connector_key]` is always `None`, same mechanism a catch-all would use) - only ever created when the user explicitly places and wires one themselves, same as any other node. Because Category and Project are each singular per expense (never two different categories, or two different projects, on the same expense), an edge between two *different* real nodes of the same one of those types could never carry any value; `is_impossible_edge` rejects such a *direct* edge with an explanatory message, both client-side at draw-time (`_tryConnect`) and server-side in `save_graph` (defense in depth). That direct-edge check isn't enough on its own though: the same impossibility exists just as much through a *chain* of intermediate nodes (a Connector hub, or even a real Tag node sitting in between) as it does through a direct edge, since once a node's inflow is provably restricted to one Category/Project (or a fixed set of them, e.g. several different income Categories all fed into one Connector), nothing downstream of it can ever carry a *different* one - this is exactly the mistake that once silently routed every expense reaching a Connector nowhere at all (5 income Categories wired through one Connector into 4 different expense Categories: every item arriving at the Connector already had one of the 5 income categories, so none of it could ever match any of the 4 downstream ones). `sankey_service.locked_identities` computes, per node and per axis (`category`/`project`), the set of identities its inflow is provably already restricted to (`None` if unrestricted - e.g. it has an unrestricted, Tag-rooted parent too), by walking the DAG backward; `is_impossible_edge_chain` uses that to reject an edge whose target's own identity isn't in its source's lock (subsumes `is_impossible_edge`'s direct case, since a Category/Project node's own lock is just its own ident regardless of its parents). `sankey_generation._check_impossible_chains` runs this over the full edge set in both `save_graph` (rejects the graph before it's persisted) and `generate()` (re-validates the already-saved graph before running the routing algorithm, so a graph that predates this check - or was otherwise saved bad - fails loudly with the offending edge named). `budget/sankey_generation.py` is the DB-facing wrapper: `_resolve_node_q` does own-if-owner-else-overlay **exact** pk matching (mirrors the visibility rule in `_tag_q`/`_cat_q` above, but those match a title *substring* for the query language, not a specific known node - reusing them here would false-positive on e.g. "Food" matching "Fast Food"; this is a new shape the existing four don't cover, not a fifth copy of one of them, and full unification is deliberately left for a follow-up rather than risking the existing four call sites). Expense scoping reuses `budget/views/_sharing.py::build_shared_qs` (shared mode: value at the feuser's own `BuddySpending` share, including for their own expenses) and the plain owner filter (individual mode: full value) - the same period + individual/shared controls as the dashboard, via `partials/_date_range_nav.html`; both branches of `_scoped_expense_qs` are additionally filtered to `type=TransactionType.EXPENSE` only, since a Sankey diagram routes spending, not income or savings deposits/withdrawals. that partial's Personal/Shared toggle drives Alpine's `$store.sharing`, so `build/js/sankey_editor.js` imports and starts Alpine itself and reads the store through that same module-local binding, never `window.Alpine` (the ES-module build of Alpine, unlike its standalone CDN build, never assigns itself to `window` - each page that uses the toggle, dashboard/expenses/sankey alike, has to import+start Alpine on its own). Generation is two-step and explicit, not live/reactive: editing the graph or changing the date range/mode never updates an already-generated chart; `POST /budget/sankey/generate/` recomputes from scratch. `generate()` never blocks on incomplete placement: any catalog node that isn't placed on the canvas is simply excluded from the graph, the same as an explicitly disabled node (`checkbox` on the node) - both are just absent from `enabled_keys`, so an unplaced node needs no special-casing beyond not being in `nodes_config` to begin with. Rendered zero-weight edges/nodes are pruned (`prune_zero_weight`) from that snapshot only, never from the saved graph. A node with real value but literally zero edges (no parent, no child) would otherwise vanish from the chart: d3-sankey computes each node's displayed value purely from its own links, silently zeroing anything with none, discarding whatever value was actually passed in - `_drawChart` (`build/js/sankey_editor.js`) splits the generated result into linked nodes (handed to `d3sankey()` as normal) and isolated ones (drawn separately as plain proportional value bars below the flow diagram, using the real backend-computed value), and the whole render is wrapped in a try/catch that shows an inline error rather than leaving the chart area silently blank on any other failure. Every linked node is also handed a `fixedValue` (d3-sankey's own escape hatch from its default `node.value = max(sum(sourceLinks), sum(targetLinks))` computation) set to our real backend-computed value: a no-op for an ordinary fully-routed node (the two already agree), but required for a node that's also a root and only partially routes its own money onward - it has no incoming links at all and its outgoing links alone sum to less than its true value, so without `fixedValue` d3-sankey would silently undersize its box to just the routed-out portion instead of its full true value. In the generated chart itself (not the editor canvas), every link is stroked in its *target* node's color rather than a flat neutral gray, so a glance at the diagram shows which downstream bucket a flow actually ends up in; a Connector node's bar renders with no on-chart text label since it's pure wiring with no meaning of its own - its name/value is still available on hover via the custom tooltip described below. Chart height is not a flat constant: `_probeColumnCounts` (`build/js/sankey_editor.js`) runs d3-sankey's own layout once at a throwaway height purely to read back each node's real rendered `layer` (not `depth` - see below) and count the most crowded column, then `_drawChart` sizes the SVG to fit that column, so a graph with many nodes stacked in one column no longer gets visually cramped/cut off under a fixed height budget. Reading `node.layer` rather than `node.depth` matters because d3-sankey's default "justify" alignment (`node_modules/d3-sankey/src/align.js`) pushes every *sink* node (no outgoing links) to the same rightmost column regardless of its natural longest-path depth - two leaves reached via a different number of hops from a root can still end up sharing one rendered column, which only `layer` (the post-alignment column) reflects; a naive depth-based or longest-path-from-root estimate undercounts exactly this case. Hovering any node/link in the generated chart, or an edge/anchor in the editor canvas, shows a custom floating tooltip (`_showTooltip`/`_moveTooltip`/`_hideTooltip`, one shared `#sankey-tooltip` div) rather than a native SVG `<title>`, which only appears after the browser's own hover delay. Every node (Tag/Category/Project and Connector alike) has a color override: a "Color" property row (regular nodes) or a small swatch dot next to the diamond (Connector, which has no property rows) opens a floating popover (`_openColorPicker`, 32 preset swatches - 8 validated categorical hues x 4 tone variants each, sourced from the `dataviz` skill's reference palette - plus a hex text field) that sets `n.color` directly - already a plain field on the node saved/loaded via `config_json` and already read back into `nodes_out` by `generate()`, so overriding it needs no backend change to take effect or persist. The in-canvas control panel (top-right overlay, same positioning the zoom +/- buttons always used) is now "the toolbar": `+ Connector node`, Save, Reset, a "Snap to grid" checkbox, then the zoom controls, all grouped in `#sankey-canvas-toolbar` - moved off the page-level bar above the canvas, which now only holds the interaction hints; the Generate button sits below the canvas instead. Snap-to-grid (`_applySnap`, `GRID_SIZE`, on by default) only affects a node or anchor while it's actively being dragged - toggling the checkbox never retroactively moves anything already placed. An edge can carry any number of user-placed "anchors" (`edge.anchors`, a plain `{x, y}` list alongside `source`/`target` - passed through `save_graph`/`generate()` untouched since both only ever read `source`/`target` off an edge dict) purely to shape the drawn line for readability; they have no effect on routing/weights. The drawn line stays one continuous, tangent-continuous curve through every anchor (`_waypointTangents`/`_edgePathFromPoints`: a cubic Bezier segment per gap, each sharing the same tangent direction with its neighbor at every anchor, plus a forced-horizontal tangent at the very first/last point so it still leaves/enters each node's socket flat) rather than a straight-line polyline, so a shaped connection looks as smooth/rounded as an unshaped one. An anchor renders as a small diamond (`_drawAnchor`) on top of its edge, draggable via `_startAnchorDrag` (snap-to-grid applies here too); right-clicking a plain point on an edge inserts a new anchor at the closest segment (`_addAnchorAt`/`_pointToSegmentDistance`, so it lands in shaping order rather than always at the end) and right-clicking an existing anchor does nothing; left-clicking an anchor deletes just that anchor, left-clicking anywhere else on the edge deletes the whole connection (anchors and all). Hovering an anchor turns it red (CSS `:hover`, signaling what a left click there would delete) without recoloring the edge underneath, since the anchor is a separate element drawn on top and captures the hover itself. A "Reset" button (`reset()`, gated behind the shared `window.confirmDialog()` irreversible-action pattern) clears every node and edge from the in-memory graph; like every other edit here, nothing is persisted until the user clicks Save afterward.

Frontend is a hand-rolled SVG canvas editor (`build/js/sankey_editor.js`), following the site's own light/dark theme via the same CSS custom properties as everywhere else (`build/scss/_sankey.scss`) - only each node's header keeps a fixed, vivid per-type accent color (project/category/tag/connector) with white text on it, the same idea as a dashboard card's colored cell, readable regardless of site theme; a bare `<button>` (`.sankey-palette-item`, the Unplaced-palette chips) needs its `color` set explicitly to `var(--text)` or it falls back to the browser's default dark button text, unreadable against `--bg-input`'s dark-mode value. Each Tag/Category/Project node is a colored header bar over a theme-aware body listing its own properties ("Priority"/"Disabled") as labeled rows, plus one blank "connector" row right after the header that carries nothing but the input (left edge) and output (right edge) sockets - deliberately its own row, never lined up with a labeled property, so a wire can never visually read as if it targets a specific value (`_socketPos` always returns the connector row's center, regardless of a node's actual height) - **except** a Connector *node* (`_drawConnectorNode`), which skips this box entirely and is instead a small unlabeled diamond (a rotated square, `CONNECTOR_SIZE`) with just its two sockets (at the diamond's left/right tips) and a small "×" to delete it: no header, no title, no Priority/Disabled rows, since a Connector's own priority is structurally irrelevant (as a child it's always evaluated last regardless of its priority number, see `build_children_order`) and it can never be disabled - the diamond shape itself is what visually says "this is pure wiring, not a real node." Wiring is click-drag-drop from either socket, with a live dashed "noodle" path following the cursor until it's dropped on another node (`_startConnect`/`_updateTempLine`/`_endConnect`). Two nodes far enough apart that they can't both fit on screen at once would otherwise be impossible to wire together without letting go to pan manually first: while a connection is being dragged, the cursor nearing the viewport's edge auto-pans the canvas toward it (`_startAutoPanLoop`/`_autoPanTick`/`_stopAutoPanLoop`, `AUTO_PAN_EDGE`/`AUTO_PAN_SPEED`), continuously via `requestAnimationFrame` rather than only on `mousemove` so it keeps scrolling even with the cursor held still right at the edge. Each tick calls `_applyTransform()` (just the `<g>` transform attribute) rather than the full `render()`, both because a pan/zoom change alone never needs nodes/edges redrawn (they're already positioned relative to that transform) and because `render()` clears `this.g`'s children, which would delete the live temp connecting line mid-drag; `_updateTempLine` is re-run every tick so the noodle keeps tracking the (screen-fixed, world-shifting) cursor position as the pan changes underneath it. New nodes placed via the palette or `+ Connector node` similarly spawn inside the current viewport (`_nextSpawnPos`/`_viewportWorldRect`, a small grid sized to what's visible, cascading with a diagonal offset once a heavily zoomed-in viewport's grid runs out of slots) rather than at a fixed canvas-origin position that could be far outside a panned-away view. Canvas navigation: scrolling empty canvas zooms centered on the cursor, not the origin (`_onCanvasWheel`/`_zoomAt` solves for the pan that keeps the world point under the cursor fixed on screen before/after the zoom change); the zoom is multiplicative and proportional to the wheel event's actual `deltaY` (`ZOOM_WHEEL_SENSITIVITY`), not a fixed step per event - a trackpad fires many small-`deltaY` events per gesture where a mouse wheel fires few large ones, so a fixed-step-per-event design (tried first) made trackpad scrolling zoom far too aggressively; scaling by `deltaY` keeps the total zoom change proportional to total scroll distance regardless of event count. The −/+ buttons (`_zoomBy`, a fixed multiplicative factor) live inside the canvas viewport itself, absolutely positioned top-right (`.sankey-zoom-group`, `.sankey-canvas-wrap` as its `position: relative` anchor) rather than in the toolbar above, since that's where a zoom control is expected to act on the thing it controls; both wheel and button zoom funnel through the same `_zoomAt`, just anchored at the cursor vs. the canvas's own center. Click-dragging empty canvas pans, with no position limits (`_startPan`/`_endPan`, gated the same way node-drag/connect already are - every interactive element stops propagation on its own mousedown, so a pan only ever starts from a genuine background click); `#sankey-canvas` sets `user-select: none` so a click-drag pan never highlights node/label text along the way, which a plain click-and-drag gesture would otherwise trigger as browser text selection. The toolbar's hint text is one block per instruction (`.sankey-hint` forces its own flex row via `flex-basis:100%`, with each instruction its own `<div>` inside it) rather than one run-on line, so it doesn't wrap mid-sentence. The Unplaced palette sits in its own full-width bar above the canvas (not a side rail) so the canvas gets the page's full width; the page itself caps at the dashboard's own 1200px `main.app-main` max-width. The generated chart itself is laid out with `d3-sankey` (bundled locally same as everywhere else).

**Participant overlay auto-matching on expense creation** (`budget/services.py::create_participant_overlays`, called from `budget/views/expenses.py` and `generate_scheduled_expenses.py`): when a real-user participant has no overlay yet, a title-matching **category** is auto-applied unconditionally (a wrong category match is just wrong -- easy to notice and fix), but a title-matching **tag** is only auto-applied when the participant and the expense owner are in the same onboarding-complete Catalog Partnership (`budget/services.py::_same_catalog_partnership`), where their tag catalogs are actually guaranteed to be the same set. Unrelated feusers never get tags auto-matched by title: a coincidental match ("Restaurant" vs "Restaurante") would assign one plausible-looking tag while silently dropping every other tag the expense should have gotten, and -- because that makes the overlay non-empty -- the expense would stop showing up on the Unclassified Expenses page above even though it's still missing most of its real tags.

**Dashboard cards** (`budget/dashboard_cards.py`): stored as `DashboardCard` with `yaml_config` only; all layout in YAML `positioning:` block. Types: `cell`, `bar-chart`, `pie-chart`, `list`, `line-chart`, `gauge`. API uses session auth (not Bearer): `GET/POST /budget/dashboard/cards/`, `PATCH/DELETE /budget/dashboard/cards/<id>/`. AI card assist (`budget/dashboard_card_ai.py`, `POST /budget/dashboard/cards/ai/`): generates/edits a card's YAML from a free-text prompt; system prompt is built live from `docs/src/docs/user-manual/dashboard/` (all child pages) plus the user's catalog and their other cards' YAML, so it stays in sync with the docs automatically. Gated by `ai_smart_create_available` (context processor) and per-user trial exhaustion; result only fills the YAML editor, never auto-saves.

**Notification classes** (ordered): `"" < soon < tomorrow < today < late < settled`; each sent at most once per expense.

**Double-submit guard** (`templates/base.html`): a global `document` `submit` listener disables every submit button in a form (`.is-loading` class, styled in `_buttons.scss`) the moment a submit event isn't cancelled, so a stray second click can't re-fire the same create/save action before the page navigates away. Applies automatically to any plain form; pages that intercept `submit` themselves (buddy consent AJAX, the date-range-warning confirm dialogs in `expense_form.html`/`express_creation.html`) call `e.preventDefault()` first, which the guard checks (`e.defaultPrevented`) and skips, leaving those flows to lock the button on their own eventual real submit. No per-page wiring needed for new create/save buttons.

**Save checks** (`window.addSaveCheck(form, check, {blocking})`, defined in `<head>` of `templates/base.html`): the single way to put validation or a confirm dialog in front of saving a form. Blocking checks (validation, return `false` to stop) run first, then warnings (return `{message, okLabel, extraLabel?, onExtra?}`) one dialog after the other; the form is submitted once via `requestSubmit()` after the last one passes. Used by the expense form's date-range warning, `buddy_expense.js`'s no-participants check and payer-approval warning, and AI Express's buddy validation + date warning; never hand-roll a page-local `submit` listener with skip flags for a new warning. `window.confirmDialog(message, okLabel, extraLabel)` resolves `'ok'`/`'extra'` (optional third button). **Missing category/tags warning** (`budget/templatetags/unclassified_warning.py` -> `budget/partials/_unclassified_save_warning_js.html`, config from `budget/unclassified.py::save_warning_config`): manual expense form, recurring expense form, and AI Express (one dialog for all selected items) warn before saving an expense that would land on the Unclassified Expenses page (same `EXCLUDED_TYPES`), but only about a field the feuser could fill in (missing category only if they own a category, missing tags only if they own a tag). One fixed text for every case. "Don't show again" posts to `unclassified_save_warning_dismiss` (403 for demo users, button hidden for them) and clears `FeUser.warn_unclassified_on_save`; the profile "Expense entry" card (`ExpenseEntrySettingsForm`, demo-blocked) turns it back on. Deliberately undocumented in `docs/src/`.

**Toast stack** (`templates/partials/_toast_stack.html`, included once by `templates/base.html`; `.toast-stack`/`.toast` in `_misc.scss`): the single, sitewide rendering path for every transient flash notification, fixed bottom-right (`position: fixed`, `column-reverse` so a new toast slots in above the corner and pushes older ones up) so appearing/disappearing never reflows page content. Two ways in: `django.contrib.messages` entries (`messages.success`/`.error`/etc., any view) are rendered server-side into the stack on page load, one `.toast toast-{{ message.tags }}` per message; `window.showToast(message, tag='success')` (defined in `base.html`, alongside `window.confirmDialog`) appends one client-side for an AJAX action that doesn't reload the page. Both paths share the same auto-dismiss timer (5s) and a manual "×" close button, wired by the same `initToast()` helper. No per-page wiring needed -- do not hand-roll a page-local flash/toast element for a new feature; call `window.showToast` (JS) or `messages.success()` (server-rendered) instead. Tag classes (`toast-info`/`-success`/`-warning`/-`error`) reuse the same color-mix recipe as `.buddy-flash`'s tag variants (still used on their own for a couple of static, non-dismissing warning boxes, e.g. `kick_dummy_confirm.html`'s "Outstanding balance" notice -- those aren't flash messages and stay put).

## Demo users (`is_demo=True`)

A demo user is a shared public account anyone can log into. Every restriction on a demo user must satisfy two hard rules:

1. **No interaction with real users.** A demo user must never be able to send emails, invitations, partnership requests, or any other out-of-band contact to a real account. Real users must equally be unable to pull a demo account into their social graph (contact, project member, partner).
2. **No sabotage of the shared demo experience.** A demo user must never be able to perform an action that degrades the demo for the next visitor: they cannot change their own name, email, or password; cannot delete the account; cannot set up 2FA; cannot generate an API key.

What demo users **can** do: change currency, financial month settings, unspent allowance action, create expenses, use AI express entry (subject to `special_ai_trial_budget`).

The demo banner (shown at every login, must be accepted) and all server-side blocks are enforced regardless of `ENABLE_DEMO_USERS`. That flag only gates login access and the landing-page advert. `reset_demo_user` (run by `run_cron`) deletes all `is_demo=True` users and recreates a fresh "Dean Demo" account once the last one has been inactive for a week.

When adding any new feature: if it sends email, modifies another user's data, or lets a user meaningfully alter their own identity/credentials, block it for demo users, both in the view (redirect/403) and in the UI (disabled/hidden).

## Transport / TLS
This app is ALWAYS deployed behind a reverse proxy that terminates TLS and forwards
plain HTTP to Gunicorn. The app itself expects HTTP and does NOT enforce HTTPS in any
way: it never redirects HTTP->HTTPS, never emits HSTS, and never inspects
`X-Forwarded-Proto`. HTTP->HTTPS redirection and HSTS belong on the proxy, not here.
Do not add `SECURE_SSL_REDIRECT`, `SECURE_HSTS_*`, or `SECURE_PROXY_SSL_HEADER`:
enabling app-side HTTPS redirect behind an SSL-terminating proxy causes an infinite
301 redirect loop. When `DEBUG` is off, the only transport hardening the app applies is
marking the session and CSRF cookies `Secure` (safe because the public edge is HTTPS).
